# 案例评估口径

## 1. 评估范围与版本

本轮按需求，从 **2026 年 10 月案例开始并作为重点**，随后完成 9 月和 8 月案例。评估日期为 2026-11-03，固定源提交为 [5056f46e123aef52c7aac9d51a03ce7a5dae53c2](https://github.com/Nuos/H3-h3-prompt-journal/tree/5056f46e123aef52c7aac9d51a03ce7a5dae53c2)。

“一个案例”按 `case-studies/` 的直接子目录划分，包含作品案例和库型案例，不按 README 中较旧的总数计数。共 **29 个案例、97 个文本文件**；其中 10 月 15 案/33 文本，9 月 6 案/25 文本，8 月 8 案/39 文本。[完整来源清单](./source-manifest.json)

所有案例目录内的文本均全文纳入，包括中英文 README、提示词、方法说明、词汇增补、TXT 及 JSON。动作迁移 JSON 包含全部节点、连线、保存参数、嵌入提示词与顶层字段。图片、音频、视频不读取、不做 OCR/转写，也不据其链接断言成片质量。源树中没有需要另行提取的案例 PDF 或办公文档。

根 [README](https://github.com/Nuos/H3-h3-prompt-journal/blob/5056f46e123aef52c7aac9d51a03ce7a5dae53c2/README.md)及共享[词汇增补索引](https://github.com/Nuos/H3-h3-prompt-journal/blob/5056f46e123aef52c7aac9d51a03ce7a5dae53c2/case-studies/VOCABULARY-EXPANSION.zh-CN.md)用于理解项目和注释来源，不另计为案例。案例链接的外部仓库、作者本机素材、未提交的 manifest/SRT 不自动扩入本轮；因此相关缺口描述限于当前文件范围。

## 2. 审阅程序

1. **固定清单。**枚举源提交目录树，按文件内容与类型识别文本，建立每案例文件清单。
2. **核验完整性。**保存全文并核对 Git blob SHA；大型文件分段阅读，JSON 按全部节点和字段阅读，检查截断并补读。
3. **先评 10 月。**优先分析其模块、参考权限、工作流、时间和状态关系，再处理较早案例。
4. **比对所有版本。**README、执行提示词、译文、词汇修订和 JSON 相互核对。注释承认问题但未修改执行稿的，说明“已记录、尚未同步”，避免当作首次发现或已修复。
5. **区分材料与判断。**每篇用来源编号和行号给出具体依据；明确作者记录、文本静态事实、审阅推断和后续建议。
6. **交叉审校。**对重点案例的数值、字段计数、有效连线参数及主要问题进行复核；收紧把阶段性规则误写成全局矛盾的表述。
7. **覆盖检查。**确保 29 个案例各有独立评估，97 个来源文件全部列入对应评估，固定源链接及行数可回查；新增内容只位于 `docs/casereview/`。

这是一轮文本与工作流结构审阅，没有执行 H3 或重新生成素材。静态计算可以确认如段长相加、时间偏移、状态数量与表达式结果；模型是否服从、画面是否自然、音画是否实际同步仍需要运行与成片检查。

## 3. 统一评价维度

| 维度 | 主要问题 |
|---|---|
| 模块构成 | 哪些模块负责输入、规划、动作、镜头、音频、状态、剪辑和验收？模块如何衔接？ |
| 方法论 | 是否给出输入职责、步骤、适用边界、失败原因与修订逻辑？是否能迁移到新任务？ |
| 输入输出 | 图片、音频、视频分别有何权力？哪些属性不变、哪些允许改变？输出如何独立提交？ |
| 时序与连续性 | 全局/局部时间是否一致？动作与音乐、镜头的关系明确吗？相邻段入出态可否核对？ |
| 文档和实现一致性 | 概览、正文、译文、库版本及工作流连线是否一致？是否有过期引用或重复权威？ |
| 可复现性 | 是否有配置、依赖、素材标识、过程记录、成功/失败样本和可判定验收？ |
| skill 化 | 适合做主流程、专项子技能还是参考库？最小封装需要补什么？ |

“标准性方法论”在本轮指项目内可重复使用的规范结构。它不表示行业标准、H3 官方规范或已经获得外部认证。人数、画幅、无对白、角度写法、动作容量及片长等规则都须保留原任务作用域。

## 4. 两个独立等级

### 方法论成熟度 M

| 等级 | 判定标准 |
|---|---|
| **M1：局部经验** | 以单例经验、提示词片段或零散禁令为主，输入职责和工作步骤不足以迁移。 |
| **M2：可复用结构** | 输入、步骤或约束已较明确，有可抽取模板/机制；决策、冲突处理、验证或修订环节仍不完整。 |
| **M3：系统方法** | 明确输入职责与编排步骤，说明边界、问题处理，并提供验收或修订逻辑；能够支撑成套流程设计。 |

M3 评价方法结构，允许实例仍有错误。方法文章写出一条规则，并不意味着全部提示词已遵守该规则。方法和实例的落差会在对应问题中单列。

### skill 就绪度 S

| 等级 | 判定标准 |
|---|---|
| **S1：参考素材** | 可作为规则、词库或示范引用；独立调用所需的输入、选择/组装步骤或验收接口尚不足。 |
| **S2：可封装原型** | 已能识别可复用任务及较完整的输入—编排—输出路径，适合开发主流程或专项原型；仍需参数化、冲突检查、依赖适配及回归。 |
| **S3：稳定性证据充分** | 在审阅范围内同时提供可执行 skill 或明确执行入口、版本化配置/依赖、跨输入回归和可复核验收记录，能界定适用范围及失败处理。 |

S3 不要求所有运行绝无失败，但要求可说明在哪些条件下可靠、如何判失败和如何恢复。本轮没有案例达到该证据要求。外部 skill 链接或单个 ComfyUI JSON 是有价值的工程线索，不能单独代替这一整套证据。

### 建议定位

- **主流程候选：**覆盖从输入理解到编排、交付/检查的主要链路，如长舞 MV、动作迁移或逆向剧情重建。
- **专项子技能候选：**围绕明确子任务工作，如接触换装、动作链组合、多人队形或手势响应。
- **参考库模块：**提供主流程按需选取的机位、纪律或局部关系素材。

定位和等级并非一一对应。动作链库具有较强方法结构，可评级 M3/S2，同时仍适合被更大的主流程调用。参考库篇幅很长，也不必因此升为主流程。

## 5. 问题优先级与证据语言

| 标记 | 含义 |
|---|---|
| **P0** | 直接影响执行稿选择、时间/状态一致性或规则可满足性；应在相应路径自动封装前处理。表示编排优先级，不是安全严重等级。 |
| **P1** | 影响清晰度、参数化、作用域保持、泛化或复现证据；可在原型建设中补齐。 |

对可合理分属不同阶段、模式或生产环节的规则，优先明确作用域，不轻易判为矛盾。例如保持距离的相机后退与拉远成大全景、演员持续微动与摄影机锁定、段内镜头与后期接缝，均需分别分析。

各篇按以下证据边界写作：

- **文本事实：**源文件实际包含的字段、时间、状态、条目和连线，可由固定提交直接复核。
- **作者记录：**“实测成功”“已核对”“没有身份漂移”等保留归属；没有样本记录时不换算成成功率。
- **审阅判断：**方法等级、模块定位、潜在冲突和 skill 路线属于本轮推断，并给出理由。
- **后续建议：**参数表、自动检查器、回归集、编译器等若未存在，明确为建议，不写成已经实现。

中文译注和词汇文件属于同一案例的解释材料，不增加独立实验数量；文件未提供某项证据，也不等于作者从未做过相关工作。

## 6. 文件结构与来源使用

每案以原目录 slug 命名 Markdown 文件，避免沿用可能重复或过期的案例编号。每篇依次提供核心结论、范围与等级、五个主体部分和全部来源清单。正文 `[S1]` 等编号对应本篇末尾文件，行号基于固定源提交的原始文本。

[source-manifest.json](./source-manifest.json)记录全部 97 个案例文本的路径、Git blob SHA、字节数、行数、原文链接与对应评估；[README.md](./README.md)提供 10 月优先索引、其余月份索引和跨案例建议。源提交发生变化时，应同时核对来源清单、相关评估及汇总表，避免旧结论被误用于新稿。
