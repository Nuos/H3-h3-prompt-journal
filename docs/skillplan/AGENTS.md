## 必须遵守

1. **保护全部原文。** 未取得针对冻结内容的后续明确修改授权时，不改写、删除、移动、重命名或格式化九个冻结文件；不要为标记冻结更新其版本、日期、链接或旧校验记录。
2. **保留已授权开发空间。** 可以继续用户已经授权、符合冻结规范的实现、测试和产物工作；文档明确留待实现的常规设计选择可在其允许范围内完成并记录。新增结果不应改写冻结文件或静默覆盖其中的强制要求。
3. **识别已有变更授权。** 用户后来明确要求修订某项冻结内容或解除锁定，即构成相应范围的授权，不要重复请求同一确认。执行时形成新版本和变更记录，说明依据、影响、差异和实际校验，保留原固定提交与冻结清单的历史。
4. **不以模糊任务改变基线。** 一般性的“继续开发”“实现计划”“优化实现”沿用已锁定要求，不自动授权削弱职责边界、四项强制架构原则、路由合同或证据要求。真正需要改变这些要求时，先明确冲突和建议变更范围。
5. **不覆盖未知编辑。** 文件校验不一致时，保留当前内容，查看差异与授权依据。不要自动重新生成清单接受漂移，也不要自动回滚或重置用户的后来修改。
6. **区分历史与实现。** 归档保持历史原文；现行架构按冻结版本解释。`planned`、41 个初始子模块提案和尚未执行的验证不能改称已实现／通过。
7. **核对范围与完整性。** 与本目录有关的变更应检查冻结成员是否保持预期内容，核对新增／修改范围和相应授权，不把格式检查当成模块或媒体效果验证。
8. **保护冻结控制记录。** `LOCK.md`、`baseline-lock.json` 和本文件属于控制记录；后续改变其政策、清单或基线同样需要对应的明确变更授权与历史记录。清单自身不做自哈希，由其 Git 提交固定。

本文件落实的是用户要求的内容冻结与变更控制，不设置操作系统只读权限、GitHub 分支保护或外部服务权限。
