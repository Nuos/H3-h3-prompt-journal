# M11.1 后端能力与版本资料

**核心摘要：** 先回答能力来自哪个模型、协议和工作流版本，再判断任务能否进入编译或导出。官方提示词语法、部署输入字段和实际生成质量分别举证。

**关键结论：** 未知值保留未知；案例片长不构成硬上限；预查可独立于完整创作计划运行。

**关键词：** CapabilityProfile、版本、来源、支持状态、能力预查。

**目录导航：** 1. 资料层次；2. 最小工作流；3. 能力冲突；4. 验收与证据。

## 1. 区分三类资料

| 资料 | 能回答什么 | 不能由此推出什么 |
| --- | --- | --- |
| 固定版本的官方提示词指南 | 五种模式、正文结构、参考标签、对白和声音语法 | 本地工作流节点名、显存需求、可接受尺寸或最大 token 数 |
| 目标部署的配置、接口定义和有版本的运行记录 | 字段位置、取值类型、枚举或范围、素材输入顺序 | 所有兼容名工作流都具有相同字段；文字要求已在视频实现 |
| 案例文字与作者报告 | 本案使用的参数、过程和经验 | 这些数值是模型能力硬限制；本轮已复现生成效果 |

`CapabilityProfile` 属于内部适配合同，不能插入 H3 模型正文。身份、动作、风格、音轨权限和故事目标由相应上游决定；能力资料只提供规划条件。

## 2. 最小工作流

1. 固定目标后端标识、模型版本、工作流版本与协议快照。无法确认的部署信息保持缺项，不把“本地 H3”当作足够精确的版本。
2. 对模式支持、输入媒体、输出时间／尺寸／帧率及参数映射逐项登记来源。来源至少可定位，并带版本与相应说明；证据等级不能由文件名或 `verified` 单词自证。
3. 将已支持、明确不支持和未证实分开。协议文档存在某模式，不自动证明所选插件或工作流已暴露该模式。
4. 比较本次实际要求与能力资料。缺少工作流资料时仍可完成协议部分；只有依赖该资料的阶段被阻塞。
5. 将能力预查和具体缺项返回 M2、M7、M9。正式编译继续使用相同版本，避免预查和导出悄悄换了 profile。

若用户明确要求长篇提示词，保留满足内容需要的完整描述。Ref2VA 的常见 350–500 英文词指引是编写建议，不能冒充 tokenizer 容量；没有对应部署证据时，不增设 500 词、某固定 token 数或时长硬上限。[R:237–239]

## 3. 能力冲突的责任回传

| 冲突 | M11 输出 | 责任方 |
| --- | --- | --- |
| 请求时长超出有证据的范围 | 实际请求值、允许范围、版本与证据 | M9 重新划分任务，M7 重新排时 |
| 参考类型／数量不被本部署支持 | 冲突的实际素材和用途 | M2 调整参考方案，必要时 M9 调整任务 |
| 画幅或帧率不支持 | 明确不支持的值及工作流依据 | 请求方与 M7／M9；涉及观看任务时 M5 |
| 没有参数路径或后端版本 | 具体缺项与可继续的文字工作 | 部署资料提供方，M11.4 |
| 只有案例声明“可以运行” | 历史来源和未复现状态 | 不能据此通过实际运行验收 |

不要静默截短、降采样、拆段、删除动作或改台词。这些变化会影响创作和时间权威，须形成明确修订请求。

## 4. 验收与证据

核对 profile 的版本与来源可解析、声明没有自相矛盾、被要求使用的模式和参数具有明确依据。源码声明、用户提供的部署资料和本轮执行记录保留各自性质。脚本核验声明与结构；不替用户连接真实工作流探测支持情况。

本包官方协议样例的运行字段保持未知。标为合成／模拟的演示 profile 用于展示参数映射合同，不是 MiniMax 的真实限制。最终任务包保留这种来源状态。

**依据：** 冻结框架 M11、路由文件的能力预查和 G2 入口；官方 R 为 `h3-ref-official.txt` 的原始一基行号。具体版本与原文哈希见 `h3-protocol-source.json`。
