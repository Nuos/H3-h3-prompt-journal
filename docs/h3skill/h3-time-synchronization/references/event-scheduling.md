# M7.2 事件排时与同步约束

## 核心任务

在既有事件语义上安排时间，说明先后、重叠、延迟、触发和容量。事件语义由 M4/M5/M6/M9 提供；M7.2 不以“时间优化”重写专业内容。

## 1. 先明确事件和比较点

为动作、摄影、声音和编辑事件保留独立 ID 与所有者。同一时刻发生的脚掌接地、镜头到位、鼓点和换装边界是不同事件，不共用一个 ID。

明确每次比较落在事件的哪个锚点：开始、峰值、接触、到位、结束。若上游已把到位或接触建成独立事件，直接引用其 ID，不再复制一份竞争事件。未知锚点保留未知，不以整条动作起点代替接触点。

事件持续时长只可依据既有要求、可信观察或清楚标记的候选设计。把“动作能否合理完成”的语义审阅与“给定起止是否大于最短预算”的数值检查分开。

## 2. 明确同步关系

令 A 为参照事件的指定锚点、B 为响应事件的指定锚点，关系写为 Δ = t(B)−t(A)。负数表示 B 提前，零表示候选同相，正数表示 B 滞后。再记录允许的偏移区间或目标偏移与容差。

| 关系 | 排时要点 | 主要审计 |
| --- | --- | --- |
| before / after | 说明比较的是开始还是结束，是否要求最小间隔 | 因果依赖不可反转；不能用开始先于开始冒充全动作已完成 |
| simultaneous / offset | 显式目标偏移和容差 | 不默认所有摄影与动作逐拍同启 |
| overlap | 两个持续区间有真实重叠，并声明所需范围 | 仅端点相等不构成正持续重叠 |
| camera lead | 相机完成到位后，目标动作峰值仍处于可观察窗口 | 检查到位时刻，不只检查运动启动 |
| camera lag | 允许滞后且不损失观看任务 | 滞后是 M5 选择，不是自动把错误合法化 |
| fixed observation | 相机固定观察区间覆盖相关事件 | 不要求每拍重启固定镜头，不冻结人物 |
| contact trigger | 接触事件提供边界触发，时间是其计划位置 | 单有时间戳不能替代触地和状态变化的因果关系 |

具体关系枚举和脚本已实现范围以 contracts.json、contract-guide 为准。本表同时包括 Agent 应核对的语义，不声称每项自然语言条件均由程序判定。

## 3. 处理容量和覆盖

按目标区间检查必须出现的事件、必要停顿和有依据的最短持续。明确允许同时发生的动作／声音关系，不把所有持续时长无条件相加；也不能用任意重叠规避已有先后约束。

运行合同分别检查三件事：只读 `timing_requirements` 约束单个事件的必要／最短／最长持续；`duration_budget` 比较明确声明为串行预算的持续总量与可用窗口，并检查事件是否落在窗口内；`capacity` 限制同一时刻的占用数量。总量通过不等于顺序正确，串行先后还须使用 `before`／`meets`，单通道不得重叠可用 `capacity=1`。

“时间线覆盖”是已声明任务、事件或观察窗口的覆盖，不要求每一声音层从 0 秒持续到片尾。静默、空镜、等待或留白均可以是设计，但应来自当前任务而非缺数据。

当容量不足：

1. 给出冲突事件、原预算、可用区间及来源。
2. 保留用户必保动作与原台词。
3. 向 M4/M6 请求内容或持续条件的修订，向 M9 请求分段／装配调整；涉及作品意图回 M1。
4. 责任方接受变更后，再基于新版本排时。

文字对白没有实测录音时可以提供带假设的候选预算，不能声称已按“真实语速”验证。不要擅自加速说话、删标点、截断句子或把正常语速改成急促表演。

## 4. 从案例抽取可选择策略

运镜纪律库提供相机提前到位的策略，多段舞蹈同时包含 1:1 同步方案；这些条件不能叠成“相机永远提前且永远同时”。由当前观看任务选择策略，保存选择理由和责任者。

触地切换案例要求先出现完整接触结果、再完成必要保持和再次抬腿；将多个事件压到同一不可区分帧会丢失语义。帧量化后还应复查正间隔、先后和允许误差，不仅检查量化前的秒数。

单镜两段生成案例说明生成边界并不自动增加故事中的镜头数。时间块、动作阶段、生成任务与 Shot 分开。

## 5. 交接

输出带来源的起止、偏移、容差和冲突；交 M7.3 换算，向 M8 提供状态检查时刻，向 M9 提供所需边界时间。向 M11 交接每个生成任务内的时间表达，避免把全片秒数直接写进局部提示。

## 方法依据

领域案例见 case-evidence 的 C01—C06；职责与回传依据冻结开发方案 M7 及模块化原则。明确约束、最小预算和量化后复验规则为 D 类实现细化；不代表真实视频已逐帧满足。
