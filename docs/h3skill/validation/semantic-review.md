# M1 独立文字试用：集成审阅

## 审阅方式与结论范围

试用执行者未参与本包编写，按本地技能资源和指定案例文字构造产物，并实际运行 CLI。根代理在试用过程中收束任务范围，随后把产物与原文逐项对照；这是有指导的前向使用记录，不是盲测，也没有执行“不使用技能”的对照实验。

本记录只评价所列文字产物的来源保真、职责边界和信息组织。没有观察或生成音视频，不评价 H3 媒体质量，不据此计算成功率，也不修改原始 CLI 结果中 `semantic`、`media` 和 `overall` 的未验证状态。

## 贴纸厨房喜剧：仅 M1.2

**审阅结果：在当前文字范围内通过；正式事件分区核对保持未验证。**

输入来自固定源版本的 README 与完整提示词。试用把原四个镜头整理为三个语义段：恶作剧成立、后果回到实施者、卡通倒地收束。段落提案仅写 `changes.paragraphs`，未建立其他子模块的权威对象。

| 审阅点 | 实际依据与判断 |
|---|---|
| 来源保真 | 请求中的 5 处案例摘录与声明的原文行号逐字一致；10 个已读资源的 SHA-256 与版本记录一致。 |
| 人物分工 | 倒盐由贴纸角色实施；真人手负责翻炒、后续收罐、轻敲头和喂食，没有调换动作归属。 |
| 约束范围 | “真人手不操作盐罐”限定在倒盐阶段；随后收罐得到保留，没有误写为全片禁止接触。 |
| 因果与观众信息 | P01 先明确同一口锅被大量加盐；P02 才把该锅食物喂给角色；P03 呈现吃下后的夸张反应。前序依赖 P01→P02→P03 与信息内容相符。 |
| 媒介与声音要求 | 平面贴纸／真实厨房对照、无盖盐罐、无对白和无配乐均保留；没有把无配乐改成全片静音。 |
| 模块边界 | 三个语义段未被写成三个镜头或生成单元；没有新增机位、秒点、人物动机或对白。 |
| 未决项 | 六个 KEEP ID 在请求正文中有文字定义，但没有 M1.1 已接受的事件分区；检查器准确保留 6 条 `keep_context_unverified`。 |

`route` 与 `check --request` 均实际退出 0，分别为 `routed` 和 `structurally_valid`。后者的 `deterministic` 仍为 `unverified`，不能把格式可用写成全部语义与依赖就绪。根代理只把原始 JSON stdout 的扩展名从 `.log` 改为 `.json`，以便正常纳入仓库；输出内容未改。

证据：[请求](narrative-trial/M1Request.json)、[提案](narrative-trial/M1Proposal.json)、[执行记录](narrative-trial/execution.json)、[原始检查结果](narrative-trial/check-result.json)、[来源复核](narrative-source-check.json)、[可读方案](narrative-trial/README.md)。

## 四人编舞 SEG10：完整 M1

**审阅结果：三个子模块的文字职责与来源分区可审查；作品输入存在未解决的来源冲突，父接受正确拒绝。**

完整 M1 在这里指意图约束、段落信息、情绪母题三个分区均形成提案，范围只覆盖已提供完整提示词的 SEG10。全片 14 段只是上下文，四个语义段不代表重新分成四个镜头或四次生成。

| 审阅点 | 实际依据与判断 |
|---|---|
| 作品与角色 | 四人身份、木墙外廊、保护／信任／重新聚合的方向与原文相符；未补造第五人、场景、道具或情节。 |
| 信息推进 | 保护弧与会合→换层与回应→扩张重组→未完动作交接，各段有不同功能，未把所有段落写成同一种增强情绪。 |
| 情绪与母题 | 相对能量、半拍回应、四人不同身体线和动作回收被记录为设计解读；没有声称测得实际音频节拍或观众感受。 |
| 来源冲突 | README 的各自象限／不越中心线，与 SEG10 的交叉、中心会合和换层并存。提案保留两方；`ISS_CENTERLINE` 为 `conflict` 且阻塞，没有擅自删除要求或改成非阻塞未知。 |
| 时长与缺证据 | 13.767 秒记为源文请求的生成窗口；93.75 BPM 和拍点仍是文本声明。真实音频、图片、视频与 cuts_manifest 未提供，未验证状态保留。 |
| Label 边界 | S1—S4 仅沿用案例 Subject 的简写，不是实际发声者 Sx；未分配官方说话人 ID。 |
| 父接受与版本 | 实际 `accept` 返回 `rejected`、退出 1，三个提案原子拒绝；唯一当前 WorkBrief 仍为空 version 0。`workbrief-proposed.json` 是带冲突的人工可读候选，不是已接受版本。 |

根代理发现首轮 `C_AUDIO` 将原文 `no lip-sync` 写成“不要求对口型”，弱化了禁止条件。试用执行者保留修改前的提案、批次与候选预览，再修正为“禁止对口型”；日志 028—030 记录修正后的提案检查、批次检查和父接受。该问题由文字对照发现，脚本结构检查没有声称能够理解这种语义弱化。

修正后仍由同一来源冲突阻塞。这里的拒绝证明已声明的冲突没有在聚合时消失，不证明案例原要求在物理上绝对不能兼容；继续生产需要明确限制的范围／优先级，或由相应专业环节提供可兼容路径。

证据：[请求](mv-trial/request-m1.json)、[三子提案批次](mv-trial/proposal-batch.json)、[实际父接受结果](mv-trial/parent-acceptance-result.json)、[当前空简报](mv-trial/workbrief.json)、[候选预览](mv-trial/workbrief-proposed.json)、[试用结果索引](mv-trial/trial-summary.json)、[可读方案与修正说明](mv-trial/README.md)。

试用日志保留当时实际运行的绝对路径。路径中仓库根之后的 `case-studies/...` 对应本仓库同名固定版本文件，原文另存于 `mv-trial/inputs/`；这些历史路径不构成技能运行依赖。原始命令日志不改写成没有实际执行过的路径。

## 对首个模块验收的影响

本次两个试用分别检验单子模块的局部交付和完整父子提案的冲突拒绝。有效输入的接受、版本递增、兄弟分区保持和影响传播另有 52 项行为测试及 9 次示例 CLI 记录。两种证据分开：案例试用检验具体文字使用，程序测试检验明确定义的合同条件；没有把两者合并成整个 H3 系统或成片质量通过。
